# 技術選定の記録

選んだ技術と、その理由の記録です。新しいものから順に書いています。

## 2026-10-26 初めて操作する人への案内(最初のポップアップと操作ガイド)

**選んだもの**: 最初に開いたときの案内のポップアップ(概要・想定機器・注記)と、画面の上に重ねる操作ガイド(自作。ライブラリは使わない)。

| 決めたこと | 理由 |
|---|---|
| 使い方の説明を文章で並べず、**実際の画面の上に、枠・番号・短いコメントを重ねる** | 文章を読むより、押す場所を見て覚える方が早い。初めて触る面接官・採用担当者が、数十秒で一通りの操作を知れる |
| 手順は、**実際に押すと次の番号に進む**(見るだけの手順だけ「次へ」「完了」) | 見ているだけでなく、操作しながら覚えられる。ボタンを押し間違えても、手順が自然に戻る |
| どの手順にも**「スキップ」**を置く | 操作を知っている人や、急いでいる人の邪魔にならない。途中で別の所を押して、進めなくなったときの出口にもなる |
| 「初回のみ」は**ブラウザの `localStorage`**に記録し、ヘッダーの「使い方」で見直せる | ログインを作らない方針なので、サーバーに保存しない。保存できない環境(シークレットモードなど)でも、例外を握りつぶして動く(その場合は、毎回出る) |
| 枠・番号・吹き出しは、**押す場所を包む `relative` の枠の中に描く** | 位置を計算せずに済む。標準の `<dialog>` は画面の最前面に出るので、ポップアップの中の印は、ポップアップの内側に置く必要がある |
| 吹き出しの文は**1 行**にし、画像や情報を隠さない場所(画面の左上、画像の左下、パネルの空いた所)に置く | 幅で 1 行と 2 行を切り替える案は、ブラウザの幅によって動きが変わり、車の絵に被ったため、やめた |
| 部位の枠は**黄色**、ガイドは**オレンジ**にする | 同じ色だと、ガイドの枠と押せる部位の枠が見分けられなかったため |
| ライブラリ(Driver.js、react-joyride など)は**使わない** | 手順が 6 つで、自作で足りる。依存パッケージが増えると、脆弱性の確認の対象も増える([セキュリティ更新の記録](security-updates.md)) |

## 2026-10-24 画面の作り(ポップアップ・工場マップ・状態の持ち方)

**選んだもの**: ポップアップは標準の `<dialog>`(`showModal()`)。画面の状態は `App.tsx` の 1 か所にまとめる。位置は、画像に対する割合で持つ。画面の流れは[画面遷移図](screen-flow.md)にあります。

| 決めたこと | 理由 |
|---|---|
| ポップアップ(案内・部位・工場マップ)は、**標準の `<dialog>`** で作る。共通の処理は `Modal.tsx` にまとめる | 背景を暗くする、Esc で閉じる、フォーカスを中に閉じ込める、が標準で付く。3 か所に同じ処理を書くと、直すときに食い違うため |
| 工場マップは、画面遷移ではなく**ボルトのポップアップの上に重ねる** | 「戻る」の操作が ✕ 1 つで済み、選んでいたボルトを持ち越せるため |
| 今の画面の状態(車両・部位・表裏・選択中のボルト・マップ・案内・ガイドの手順)を、**`App.tsx` の `ViewState` に 1 か所**で持つ | あとから URL に持たせる形に切り替えやすくするため。戻る操作は、まず ✕ で始め、使いにくければ URL に切り替える |
| 車両の上の部位、部位の上のボルト、マップの上の棚の位置を、**画像に対する割合(0〜1)**で描く | 画像の表示サイズが iPad と PC で違っても、押せる範囲や印がずれないため。画像と同じ縦横比の枠の中に、`%` で絶対配置する |
| ボルトの印は、**押す前は透明**にする | ボルトの絵をそのまま見せたいため。色が出るのは、ホバー・押している間・選択中だけ |
| ホバーの色は、Tailwind の `hover:` に任せる | Tailwind v4 は `hover:` を `@media (hover: hover)` の中に出力する(ビルドした CSS で確認)。マウスのない iPad では色が出ず、タップした後に色が残らない |
| ボルトの詳細パネルの高さは、**左の画像の列に固定**し、収まらない分だけパネルの中でスクロールさせる | 類似ボルトが多いと、ポップアップごと画面からはみ出したため |
| 取得した情報には、**どの ID のものか**を一緒に持たせる | ID を切り替えた直後に、前の ID の情報が一瞬出るのを防ぐため。`useEffect` の中で状態をリセットする書き方も避けられる |
| 類似ボルトの表は、**押せない**ものにする | 間違えて、似たボルトの詳細を開かないため。違いの説明を読ませるのが目的 |

**確認方法**: Chrome をリモートデバッグ(DevTools Protocol)で操作し、押す → スクリーンショットを撮る、を繰り返しました。1366 × 1024 と 1024 × 768 で、メイン画面がスクロールなしで収まり、ポップアップが画面内に収まることを確認しています。実機の iPad(横向き)でも、動作と画面に問題がないことを確認しました。

## 2026-10-24 画面のスタイルは Tailwind CSS v4

**選んだもの**: Tailwind CSS v4(`@tailwindcss/vite` で導入)。ポップアップとセレクトボックスは、ブラウザ標準の `<dialog>` と `<select>` を使い、UI 部品のライブラリは入れません。

**比べたもの**

| 候補 | 判断 |
|---|---|
| 普通の CSS(CSS Modules) | 依存が増えない。ただ、ファイルが長くなりやすく、名前の管理が手間 |
| **Tailwind CSS v4** | **採用**。クラス名を JSX に直接書けて、色・余白は `@theme`(CSS 変数)にまとめられる。現在も主流で、最新版は 4.3.3(2026-07-16 公開)。Vite 8 に対応 |
| shadcn/ui、HeroUI などの UI 部品ライブラリ | 不採用。このアプリは、車両画像の上の押せる範囲、ボルトの印、工場マップ、棚の絵と、自作の表示が中心。ライブラリの部品が役に立つのは、ボタンやセレクト程度。パッケージが増えると、脆弱性の確認の対象も増える |

**理由**
- 画面の大部分が自作の表示なので、「部品が揃うこと」より、「スタイルを短く、書き間違えにくく書けること」を重視した
- ポップアップは `<dialog>`(Esc で閉じる、背景を暗くする、フォーカスを閉じ込める、が標準で備わる)で足りる
- 色(紺のグラデーション、薄い灰色)や余白は、`@theme` に集め、画面全体で統一する

**導入の手順**: 入れる前に、最新版の公式の情報と `npm audit` を確認し、[セキュリティ更新の記録](security-updates.md)に残しました。バージョンは `4.3.3` に固定しています(`^` なし)。導入は 2026-10-24 です。

## 2026-10-23 API は閲覧専用で、5 つに絞る

**選んだもの**: データの登録・変更・削除ができない API を 5 つ(車両、部位、ボルト、部品棚)。一覧は [README](../README.md#api) にあります。

- **返す形は Pydantic のモデルで決める**: 返す JSON の形がコードに書いてあり、API の説明ページ(`/api/docs`)も自動で作られる。`numeric` の列(位置の割合)は、SQL で `::float` に変換して、JSON で数値として返す
- **説明ページを `/api/docs` に置く**: Vercel では、`/api/(.*)` だけがバックエンドに渡るため、FastAPI 標準の `/docs` は画面側に回ってしまう
- **接続はリクエストごと**: サーバーレスでは、接続を持ち越せない。接続の使い回しは、Neon の接続プールに任せる
- **画像は API で返さない**: DB には、`/images/...` のパスだけを入れ、画像のファイルは `frontend/public/` から配信する
- **存在しない ID は 404**、数字でない ID は 422(FastAPI の自動の検証)

## 2026-10-22 データの設計

**選んだもの**: PostgreSQL の 10 テーブル(車両、部位、ボルト、ボルトの取り付け位置、部品棚、ボルトと部品棚の対応、類似ボルト、工区、所番地、メーカー)。テーブル定義は [backend/schema.sql](../backend/schema.sql)、ダミーデータは [backend/seed.sql](../backend/seed.sql)。

| 決めたこと | 理由 |
|---|---|
| ボルトと部品棚は**多対多**(間に `bolt_shelf` を置く) | 1 つのボルトが複数の棚に置かれ、1 つの棚にも複数のボルトが入るため |
| 工区・所番地・棚、メーカー・背番号を**別のテーブル**に分ける | 1 つの表に並べると、同じ所番地が別の工区に属するような食い違いが入りうるため |
| 画像の上の位置は、**画像に対する割合(0〜1)**で持つ | 画像の表示サイズが変わっても(iPad と PC で)、位置がずれないため |
| 部品番号・所番地・棚番号などは、**文字列**で持ち、桁数を `CHECK` 制約で縛る | `012` のような先頭が 0 の番号が、数値だと `12` に変わってしまうため |
| 類似ボルトは、**1 組を 1 行**で持つ(`bolt_id < similar_bolt_id`)。検索のときに、どちら側から見ても出るようにする | 同じ組を 2 回登録すると、食い違いが入りうるため。違いの説明を持つ列も追加した |
| 類似ボルトは、自動で計算せず**手作業で登録** | 現場の「間違えそうなもの」という感覚を、そのままデータにする。サイズや規格だけでなく、見た目や置き場所の近さも関わるため |
| 工場マップは、**draw.io の図を背景**にして、印をコードで重ねる。棚の絵は、**コード(CSS の格子)**で描く | 図はすでに描けており、棚の四角 50 個の位置を数字で書くより早く、正確なため。棚の段数・列数がデータで決まるので、格子はコードで描ける |
| 車両画像の上の「押せる範囲」を、部位ごとに `area_x`、`area_y`、`area_w`、`area_h` で持つ | 画面の操作を具体的に考える中で、「画像のどこを押すと、どの部位が出るか」が足りないことに気づいたため |
| ログイン機能と画像のアップロードは作らない | 誰でも登録なしで試せる。サーバーにファイルを保存しないので、ファイルが保存されない環境でも問題が起きない。認証まわりのリスクを持ち込まない |

データは、すべて架空のダミーです。画像は、AI の画像生成機能と draw.io で作りました([README](../README.md)の「画像・データについて」)。

## 2026-10-21 公開先は Vercel + Neon

**選んだもの**: 画面と API を **Vercel**(無料の Hobby プラン)、DB を **Neon**(無料プラン、シンガポール)。

**比べたもの**

| 候補 | 判断 |
|---|---|
| **Vercel + Neon** | **採用**。Vercel は FastAPI を公式にサポートし、画面と API を同じ場所にまとめられる。スリープ待ちがない。Neon は、無料プランが恒久的で、上限を超えても課金されず、スリープしてもデータは消えない |
| Render の無料 PostgreSQL | 作成から 30 日で期限切れになり、削除される |
| Supabase | 1 週間アクセスがないと停止する。公開後に放置されると、見られなくなる恐れがある |
| Fly.io、Railway、Google Cloud Run、Koyeb | 無料枠がない、試用が期限切れになる、カード登録が必須、本番用途は不可、のいずれかだった |
| GitHub Pages | 静的サイト専用で、Python と DB が動かない |

**構成と設定**
- 画面と API の同居は、**Vercel Services**(`vercel.json`)。`frontend/` と `backend/` を分けたまま、`/api/(.*)` を API、それ以外を画面に振り分ける。ベータ版なので、仕様が変わる可能性がある
- **関数のリージョンは `sin1`(シンガポール)**: 関数は、リクエストのたびに DB へ接続する。DB と同じリージョンに置くと、往復が短くなる。日本(`hnd1`)との比較は、実測していない
- **Neon は接続プール(`-pooler`)で接続する**: サーバーレスでは接続が増えやすく、DB 側の接続数の上限に達しやすいため。Neon のプールは PgBouncer の transaction モードで、psycopg 3.2 以降は、条件つきで対応している(使用中の 3.3.6 は条件を満たす。公式ドキュメントで確認し、本番での読み書きも確認した)
- **接続先は環境変数 `DATABASE_URL` で渡す**: パスワードを含むので、コードに書かない。ローカルは `backend/.env`、Neon は `backend/.env.neon` に置き(どちらも `.gitignore` で除外)、リポジトリには、ダミー値だけの `.env.example` を載せている。本番は、Vercel の環境変数に設定している

## 2026-10-21 ライブラリの選び方

| 対象 | 選んだもの | 理由 |
|---|---|---|
| DB ドライバ(Python) | **psycopg 3**(`psycopg[binary]`) | 生の SQL をそのまま実行でき、SQL を自分で書いて仕組みを理解する方針に合う。psycopg2 の後継で、新規なら 3 が自然。`[binary]` は、ビルド済みの部品を入れる指定で、環境による失敗が少ない。値は `%s` のプレースホルダで渡し、SQL に直接埋め込まない |
| ORM | 使わない(今は) | まず、どんな SQL が実行されるかを理解したい。テーブルが増えたら、検討する |
| 環境変数 | **python-dotenv** | `.env` から接続先を読む。本番では、`.env` がなくても、環境変数をそのまま使える。pydantic-settings は、項目が 1 つの今は過剰 |
| バージョン | `==` で固定 | ローカルと本番で、同じ環境にするため。更新は手動なので、[定期的に確認](security-updates.md)する |
| パッケージ管理(フロント) | **npm** | Node.js に標準で付属し、追加の導入が不要。Vercel も対応している。Yarn・pnpm は、この規模では、手間の割にメリットが小さい |
| ビルドツール | **Vite**(8.x) | 公式のテンプレート(`create-vite`)が入れる最新の安定版。新規で作るので、古い版にする理由がない |

## 2026-10-13 言語・フレームワークの選び方

| 対象 | 選んだもの | 比べたもの・理由 |
|---|---|---|
| Node.js | **24(LTS)**。`fnm` で導入 | 最新版や奇数版(25 など)は、長期サポートがなく、すぐに終了する。LTS は、セキュリティ修正が長期間続く。`fnm` なら、プロジェクトごとに切り替えられ、のちに移行もしやすい |
| Python | **3.14** 系。仮想環境は標準の `venv` | Vercel が対応するのは 3.12・3.13・3.14。3.15 は公開されたばかりで、対応状況が未確認なので使わない。uv や pyenv は、学習する道具を増やさないため、見送った |
| DB | **PostgreSQL 18**。ローカルは Homebrew 版 | 業務でも広く使われ、学習した SQL がそのまま活かせる。本番の Neon も 18 に対応。Docker は、今回は不要な複雑さが増えるため、使わない |
| フロント | **React + TypeScript(Vite)**。Next.js は使わない | バックエンドを Python で別に作るため、API まで持てる Next.js とは役割が重なる。Vite は軽く、学習する範囲が小さい |
| バックエンド | **FastAPI**。Django と比較して決定 | 画面を React で別に作るので、API に特化した FastAPI が合う。Django の強み(テンプレート、管理画面、認証)は、今回ほとんど使わない。ORM を強制されず、生の SQL を選びやすい。API の説明ページが自動で作られる |

**FastAPI と Django の比較**

| 観点 | FastAPI | Django |
|---|---|---|
| 性格 | API 専用の軽量。必要な部品を自分で選ぶ | 全部入り(ORM、マイグレーション、認証、管理画面) |
| 今回の構成との相性 | 画面は React で別に作るので、API だけ作る形に合う | 画面(テンプレート)機能を使わず、API 用の追加ライブラリが必要 |
| DB 操作 | ORM が標準では付かず、生の SQL を選びやすい | ORM が標準で付く(生の SQL も書ける) |
| 管理画面 | なし | 標準で付く(ログインが前提) |
| API の説明ページ | 自動で作られる | 追加のライブラリが必要 |

Django を選ばなかったことで失うもの: 標準の管理画面。ただし、ログインなしの方針なので、今回は使わない。
